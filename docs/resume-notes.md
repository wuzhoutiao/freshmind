# FreshMind 简历与面试说明

## 推荐项目名称

**FreshMind 智能食材临期与菜谱推荐系统**

推荐技术标签：`Java 17 / Spring MVC / MySQL / Redis / JUC / JPA / 通义千问 / HTML/CSS/JavaScript / JUnit`

## 可直接放入简历

1. 基于 Spring MVC、MySQL 和 Redis 构建一体化食材管理网站，由 Spring Boot 同源托管响应式页面与 REST API，实现库存增删改查、保质期计算、临期看板及 Redis TTL 会话。
2. 接入通义千问 JSON 结构化输出，根据用户库存生成菜谱候选；在 Java 侧执行食材白名单校验、命中率重算和临期加分排序，避免直接信任模型输出。
3. 对标准化库存生成 SHA-256 指纹，以“用户 + 库存指纹 + 模型/提示词版本”为键缓存 AI 候选，并提供超时、错误与非法输出降级，减少重复调用和外部服务故障影响。
4. 设计每日临期扫描任务，使用有界 `ThreadPoolExecutor` 并行生成站内提醒，通过 `CallerRunsPolicy`、唯一约束和优雅停机控制任务积压与重复执行。
5. 使用 MySQL 事务和版本字段避免库存并发更新丢失，并以 JUnit、MockMvc 验证日期边界、越权访问、推荐规则、缓存键和模型输出校验。

简历只选择其中 2～3 条，不要写成技术清单。

## 高频追问

### 为什么不是 Agent？

当前需求只有一个明确目标：根据库存生成一批结构化候选。没有搜索、下单等工具，也不需要模型自己规划步骤。单次 LLM 调用配合确定性的 Java 校验更容易测试、控制费用和排查错误，所以如实称为“结构化生成 + 规则重排”。

### 为什么选择网站而不是 Android？

项目重点是展示后端业务、数据库、缓存和并发处理。网站只需启动一个 Spring Boot 进程，面试时打开浏览器即可完整演示；Android 还需要模拟器、网络地址适配和另一套构建环境。保留一种界面可以避免两套客户端逻辑长期不一致。

### 为什么不用 React 或 Vue？

当前只有概览、库存、菜谱和提醒四个主要页面，原生 HTML/CSS/JavaScript 已能完成响应式布局和 API 交互。页面由 Spring Boot 同源托管，不需要 Node.js 构建、跨域配置和独立部署，更符合以 Java 后端为主的简历定位。

### 为什么删除菜谱表？

固定菜谱和动态库存容易错配，还要持续维护种子数据。现在 MySQL 保存账号、食材目录、库存和提醒这些稳定事实；菜谱是可再生成的派生数据，用短期 Redis 缓存即可。代价是首次推荐依赖外部模型，因此增加了超时和本地降级。

### 为什么不能直接返回模型结果？

模型可能输出不存在的食材、重复项、负数数量、空步骤或夸大的推荐分数。后端把食材目录当白名单，整道菜校验通过后才重新计算命中率和临期分数。模型负责创造性，Java 负责业务正确性。

### 缓存键为什么包含库存指纹？

仅用用户 ID 会在库存变化后返回旧结果。指纹包含标准食材名、数量、单位、到期日和临期状态；任何相关变化都会产生新键。模型、提示词或食材目录变化也会换版本。`limit` 只是结果裁剪，不应触发新的模型调用。

### 模型不可用怎么办？

客户端设置连接和读取超时。未配置 key、HTTP 错误、解析失败或候选全部不合法时，服务用当前已知食材生成简单降级结果。错误和空结果不作为成功调用长期缓存，日志也不输出密钥或上游正文。

### API key 如何保护？

只从 `DASHSCOPE_API_KEY` 环境变量读取，配置对象的 `toString()` 固定显示 `<redacted>`；代码、YAML、HTTP 示例和测试都不保存真实 key。密钥一旦出现在聊天、截图或提交中就应轮换。

### 为什么首页不直接返回推荐？

模型首次调用可能需要数秒。Dashboard 只返回库存统计，推荐由独立接口加载，这样首页不会被模型延迟拖慢，也方便单独重试和展示加载状态。

### 为什么登录信息放 Redis？

会话需要过期、退出和跨实例共享。Redis TTL 可以直接表达生命周期；退出时删除 key。测试使用内存实现同一接口，不依赖外部环境。

### 为什么不用 JWT？

项目更关注本人熟悉的 Redis。服务端会话可以立即失效，逻辑也容易演示。代价是每次鉴权需要访问 Redis，因此需要关注 Redis 可用性。

### 线程池参数怎么考虑？

提醒任务包含数据库写入，不是纯 CPU 计算。学习项目没有真实压测数据，因此不声称参数最优；小线程数和有界队列先保护数据库，`CallerRunsPolicy` 在过载时形成反压并避免静默丢任务。

### JVM 锁能替代数据库版本号吗？

不能。`synchronized` 或 `ReentrantLock` 只能协调同一个 JVM 的线程；多实例时无法保护另一个进程。数据库版本字段在最终写入点完成校验。

### 为什么没有使用 Netty、Dubbo、ZooKeeper？

FreshMind 当前是普通单体管理系统，没有长连接协议、跨服务 RPC 或服务发现需求。强行加入会增加部署和排查成本；未来若独立推荐服务并出现真实跨服务调用，再评估 Dubbo 和 ZooKeeper。

## 不要声称

- 不要写“Agent”“AGI”“RAG”“模型微调”或“向量数据库”，项目没有这些实现。
- 不要写“支撑百万并发”或“性能提升 xx%”，因为没有压测数据。
- 不要把项目描述成微服务或分布式系统。
- 不要把原生 JavaScript 页面包装成大型前端工程或前后端分离部署。
- 不要声称 AI 结果完全可靠；亮点恰恰是后端校验和降级。
- 不要把 Redis、JUC 的使用夸大为解决所有并发问题。
